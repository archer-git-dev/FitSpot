# FitSpot — запуск и проверка блока А

Панель включает вход/регистрацию, подтверждение email, восстановление, профиль,
недельные интервалы, услуги и общие правила. Публичной записи пока нет.

## Первый запуск на другом компьютере

Требуются Docker Compose, PHP 8.3+ и Composer для установки зависимостей,
Node.js 24 и npm для сборки. PHP-команды приложения и тесты запускайте в контейнере:
там есть PostgreSQL, Redis и GD с JPEG/WebP.

Из корня проекта:

```sh
composer install
npm ci
# Только если .env отсутствует:
cp .env.example .env
npm run build
docker compose up -d --build
# Только для нового окружения без APP_KEY:
docker compose exec app php artisan key:generate
docker compose exec app php artisan migrate
```

Не перезаписывайте существующий `.env` и не меняйте ключ рабочего приложения.
Compose задаёт внутренние адреса db/redis/rabbitmq/mailpit. Остальные значения,
включая credentials БД/RabbitMQ, читаются из `.env`; они должны совпадать с
параметрами соответствующих контейнеров. Существующий PostgreSQL volume сохраняет
свои старые credentials даже после изменения `.env` — они не обновляются автоматически.

Панель: http://localhost:8080. Почта разработки: http://localhost:8025.
APP_URL должен соответствовать адресу, с которого открывается панель, иначе
подписанные ссылки подтверждения будут вести на другой host.

```sh
# Явно создать демо, только local/testing, без изменений существующих аккаунтов:
docker compose exec app php artisan fitspot:demo
```

Демо: `demo@fitspot.test`, пароль `FitSpotDemo123!`. Не используйте демо в production.
Повторный вызов команды не сбрасывает данные или пароль.

## Разработка

```sh
npm run dev
```

При использовании Vite с Docker открывайте сервер Vite с разрешённым host
и проверьте доступность его URL из браузера. Для простого просмотра достаточно
`npm run build`, отдельный сервер Node в production не нужен.

Фото хранятся в закрытом local storage и выдаются только владельцу через `/app/photo`.
`storage:link` для фото тренера не требуется. PHP-процессу нужны права записи
в storage и bootstrap/cache.

## Тесты

Основные проверки используют отдельную БД `fitspot_test`, никакие рабочие данные
в ней не должны храниться. Создать её один раз:

```sh
docker compose exec db sh -c 'createdb -U "$POSTGRES_USER" fitspot_test'
```

Если база уже существует, повторно создавать её не нужно.

```sh
docker compose exec app composer test
# Или напрямую:
docker compose exec app vendor/bin/phpunit -c phpunit.postgres.xml
npm run typecheck
npm run build
docker compose exec app vendor/bin/pint app config database routes tests bootstrap/app.php bootstrap/providers.php
```

Защитная проверка в tests/TestCase.php выполняется до подготовки таблиц: тесты
не стартуют, если подключение указывает на другую базу или DB_URL.
PHPUnit-пробы Telegram подписывают собственные RSA-токены и подменяют JWKS HTTP;
это проверка криптографии и сценариев аккаунта, а не имитация production-входа.

```sh
npx playwright install chromium
npm run test:browser
```

Браузерный тест работает только против окружения разработки с Mailpit и рабочими
RabbitMQ workers. Он создаёт отдельного пользователя `browser-...@example.test`,
подтверждает email через локальную почту и проверяет сохранение настроек,
мобильные страницы и восстановление пароля. Письма реальным адресатам не отправляются.
При повторных быстрых прогонах могут сработать настоящие лимиты запросов — дождитесь
их сброса; тест не отключает production-защиту. Адреса можно задать через
FITSPOT_TEST_URL и MAILPIT_URL. Не запускайте этот тест против production.

```sh
node scripts/benchmark-panel.mjs
```

Нагрузочная проверка выполняет 200 запросов при 20 одновременных клиентах:
100 чтений профиля и 100 сохранений текущих правил на отдельном демо-аккаунте.
Правила не изменяются, но события обновления реально отправляются.
Параметры: FITSPOT_TEST_URL, FITSPOT_BENCH_EMAIL, FITSPOT_BENCH_PASSWORD.
Скрипт завершится с ошибкой при HTTP-ошибках или p95 > 500 мс.
Основная метрика — HTTP-время ответа сервера (при сохранении до ответа 303).
Отдельно выводится save_with_redirect: полное время сохранения с последующим чтением
страницы. Цель 500 мс применяется к серверному ответу, а не к сумме двух запросов.
Аппаратное окружение влияет на результат. Приватное приложение обслуживает стандартный PHP-FPM
pool, Redis-кеш и PostgreSQL 16.

## Очередь и письма

Supervisor запускает два `queue:work rabbitmq --queue=mail,default` и scheduler.
Queued notifications имеют три попытки и паузы 10/60/300 секунд. PostgreSQL хранит
failed_jobs; очередь не переключается на Horizon или database автоматически.
Повторная доставка задачи может повторно отправить письмо, но не создаёт аккаунт
и не меняет профиль, график или услуги.

```sh
docker compose exec queue supervisorctl -c /etc/supervisor/supervisord.conf status
docker compose exec app php artisan queue:failed
```

При восстановлении сбоя сначала исправьте SMTP/RabbitMQ, затем повторите конкретную
failed job через `queue:retry ID`. Пользователь также может повторно запросить письмо.

В Docker SMTP направлен в Mailpit для разработки. Для production нужна отдельная
конфигурация Compose/деплоя с настоящим SMTP, HTTPS, APP_DEBUG=false и защитой
служебных портов. Текущий Compose не является production-деплоем.

## Telegram Login

Создайте бота и разрешённые origins в BotFather → Login Widget. Укажите
TELEGRAM_CLIENT_ID и используйте подпись RS256. FitSpot использует официальный JS
Login API с проверкой id_token через JWKS и nonce. CLIENT_SECRET сохранён как
конфигурационный параметр для возможного OIDC flow; текущий JS flow его не использует.
Не передавайте secret в браузер. Разрешение отправлять сообщения и бот-администратор
в блоке А не подключаются.

После изменения окружения перезапустите PHP/queue и очистите config cache.
Проверьте реальную регистрацию, вход, привязку и подтверждение личности в Telegram
на разрешённом домене. Не задавайте заголовок COOP same-origin: он блокирует popup;
при необходимости используйте same-origin-allow-popups.

Без Client ID и разрешённого домена панель честно показывает недоступность Telegram.
Текущая локальная приёмка не включает production Telegram и production SMTP.

## Примечания модели

Недельные интервалы хранятся в минутах местного дня тренера; технические даты — UTC.
24:00 — только конец интервала. Соседние интервалы объединяются. Замена недели
транзакционная с блокировкой пространства. Изменение часового пояса сохраняет
местные часы, потому что бронирований пока нет.

Цена услуги — целые копейки за участника. Сплит имеет два места; онлайн/очно —
независимый формат. Выключенные услуги сохраняются. Физическое удаление не доступно.
Рекомендованный slug имеет суффикс ID для уникальности; вручную его можно изменить.
Индексы БД защищают slug, email, владельца и Telegram identity от гонок.

При ошибке unique, возникшей между проверкой и сохранением, интерфейс получает
обычную ошибку поля, а не SQL или stack trace. События Laravel отправляются только
после commit; внешние обработчики последующих модулей должны быть queued.

PostgreSQL: 50 тестов, 209 проверок; Playwright: полный сценарий прошёл.
TypeScript, production-сборка и Pint прошли. При 20 клиентах и 200 запросах:
p95 чтения — 247 мс, сохранения — 237 мс, сохранения вместе с переходом — 436 мс;
ошибок — 0. Окружение: локальный Docker, PHP 8.3.35/FPM, Nginx, PostgreSQL 16,
Redis 7. Реальный Telegram Login и production SMTP требуют внешней настройки.
