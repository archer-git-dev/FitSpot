# Техническое задание: FitSpot, модуль 1, блок А — панель управления тренера

## 1. Цель и итоговый результат

Блок А позволяет частному тренеру создать аккаунт и самостоятельно настроить рабочее пространство для будущей онлайн-записи клиентов.

После завершения разработки тренер сможет:

- Зарегистрироваться по email или через Telegram.
- Войти любым подключённым способом и восстановить доступ по email.
- Заполнить профиль и выбрать персональный адрес страницы.
- Указать часовой пояс.
- Настроить повторяющийся недельный график.
- Создать каталог услуг.
- Задать общие буферы и правила записи.
- Изменять настройки с компьютера и телефона.

Результат блока А — работающая панель с сохранением данных и изоляцией аккаунтов. Настроенные данные станут основой для клиентской самозаписи в блоке Б.

### Границы разработки

В этот блок входят авторизация, рабочее пространство, график, услуги и правила.

В последующих блоках реализуются:

- Публичный виджет и бронирование.
- Расчёт свободных слотов и алгоритм Zero-Gap.
- Записи, переносы и отмены тренировок.
- Telegram-уведомления и сервисные команды бота.
- Google Calendar и Telegram Mini App.

Пакеты, клиенты, дневник тренировок, AI, платежи и тарифные ограничения также не входят в блок А.

Настройки отмен и переносов здесь сохраняются; применять их к бронированиям начнёт блок Б.

## 2. Архитектура и техническая основа

### 2.1. Формат приложения

Используем текущее Laravel-приложение. Модуль расписания изолируется внутри него, без отдельного сервера и отдельного развёртывания.

Один пользователь на этом этапе является одним тренером и владеет одним рабочим пространством.

Система должна поддерживать множество независимых тренеров. Команд, сотрудников и переключения между пространствами пока нет.

### 2.2. Стек

| Область | Решение |
|---|---|
| Backend | PHP 8.3+, Laravel 13 |
| Интерфейс | Vue 3, TypeScript, Inertia, Tailwind CSS 4 |
| Авторизация по email | Laravel Fortify, серверные сессии |
| Основная БД | PostgreSQL 16 |
| Кеш, блокировки, ограничение запросов | Redis 7 |
| Фоновые задачи | RabbitMQ и обычные Laravel workers |
| Веб-сервер | Nginx + PHP-FPM |
| Процессы очередей | Supervisor |
| Проверки | PHPUnit, Laravel Pint, сборка Vite, браузерные сценарии |

Fortify предоставляет серверные механизмы регистрации, входа и восстановления; страницы для них создаём на Vue/Inertia. [Документация Fortify](https://laravel.com/framework/docs/13.x/fortify).

Horizon не добавляем. SSR — серверную генерацию Vue-страниц — для закрытой панели не используем.

### 2.3. Разделение ответственности

В модуле используем следующую цепочку:

**Controller → Service → Repository → PostgreSQL.**

- Контроллер принимает запрос и возвращает страницу или результат.
- Form Request проверяет входные данные.
- Policy проверяет право тренера работать с объектом.
- Сервис выполняет бизнес-операцию.
- Репозиторий выполняет запросы к данным.
- Доменные события сообщают о завершённых изменениях.

Не создаём универсальный репозиторий «для всех сущностей». Репозитории соответствуют конкретным задачам пространства, графика и услуг.

Авторизация остаётся общей частью приложения, а настройки расписания размещаются в отдельном модуле.

### 2.4. Внешние запросы

Отправка email выполняется через очередь RabbitMQ. Бизнес-интеграции Telegram и Google в следующих блоках также будут работать через очереди.

**Подтверждённое исключение:** проверка Telegram-входа может обращаться к внешнему серверу синхронно. Такие запросы имеют конечный таймаут; публичные ключи проверки кешируются.

## 3. Регистрация, вход и управление доступом

### 3.1. Регистрация по email

Форма содержит:

- Имя.
- Email.
- Пароль.
- Подтверждение пароля.

Правила:

- Email нормализуется и должен быть уникальным.
- Пароль — минимум 12 символов.
- Пароль хранится только в виде хеша.
- Аккаунт и его единственное пространство создаются в одной транзакции.
- После регистрации отправляется письмо подтверждения email.

До подтверждения email доступны только экран подтверждения, повторная отправка письма, исправление адреса и выход.

Рабочая панель открывается после подтверждения.

### 3.2. Регистрация через Telegram

На страницах регистрации и входа размещается кнопка Telegram.

Используем актуальную Telegram Login library. Сервер проверяет подпись полученного токена, его срок действия, получателя, источник и одноразовый `nonce` — случайное значение, связывающее ответ Telegram с конкретной попыткой входа. Декодированных данных от браузера недостаточно. [Документация Telegram Login](https://core.telegram.org/bots/telegram-login).

Для проверки подписей используем `firebase/php-jwt`; поддерживаем стандартную подпись RS256.

Сценарий нового пользователя:

1. Пользователь подтверждает вход в Telegram.
2. FitSpot проверяет токен.
3. Пользователь вводит email.
4. FitSpot отправляет письмо подтверждения.
5. После подтверждения пользователь получает доступ к панели.

Пароль при Telegram-регистрации необязателен. Его можно установить позднее в настройках доступа.

Временное состояние регистрации ограничено по времени и не даёт доступа к данным панели.

### 3.3. Связь двух способов входа

В настройках доступа тренер может:

- Установить или сменить пароль.
- Подключить Telegram.
- Отключить Telegram, если остаётся доступ через подтверждённый email и установленный пароль.

Нельзя отключить последний доступный способ входа.

Telegram связывается с аккаунтом по проверенному постоянному идентификатору, а не по username или имени. Один Telegram-аккаунт нельзя привязать к двум пользователям FitSpot.

Совпадение email или имени не приводит к автоматическому объединению аккаунтов. При существующем email пользователь сначала входит в имеющийся аккаунт, затем подключает Telegram.

Смена email требует повторного подтверждения личности и подтверждения нового адреса. До этого действующим остаётся старый адрес.

### 3.4. Восстановление пароля

Реализуем стандартный процесс:

1. Запрос восстановления по email.
2. Отправка письма через очередь.
3. Переход по одноразовой ссылке.
4. Установка нового пароля.
5. Возврат на страницу входа.

Ссылка действует 60 минут. Ответ формы не раскрывает, зарегистрирован ли указанный email.

Для Telegram-аккаунта с подтверждённым email восстановление также позволяет установить пароль.

### 3.5. Безопасность доступа

Обязательны:

- CSRF-защита форм.
- Обновление идентификатора сессии после входа.
- Завершение сессии при выходе.
- Ограничение частоты входа, регистрации и отправки писем.
- Защита от повторного использования Telegram-токена.
- Запрет передачи секретов и паролей в свойства Vue-страниц.
- Отсутствие токенов авторизации в логах.

Повторная отправка писем доступна не чаще одного раза в минуту. Попытки входа ограничиваются по сочетанию адреса email и IP.

## 4. Рабочее пространство и профиль

### 4.1. Поля

| Поле | Требование |
|---|---|
| Имя тренера | Обязательно, до 100 символов |
| Фото | Необязательно |
| Описание | Необязательно, до 2 000 символов |
| Телефон | Необязательно, международный формат |
| Название места проведения | Необязательно, до 200 символов |
| Адрес | Необязательно, до 500 символов |
| Часовой пояс | Обязательно, из списка IANA |
| Персональный `slug` | Обязательно, уникальный |

Контактный email относится к аккаунту. Автоматически публиковать его не будем.

У пространства пока одно основное место проведения. Для услуги можно указать отдельное место, если оно отличается.

### 4.2. Персональный адрес

Будущий адрес клиентской страницы:

`{PUBLIC_BASE_URL}/p/{trainer_slug}`.

Домен задаётся конфигурацией; не предполагаем, что `fitspot.me` уже принадлежит проекту.

Правила `slug`:

- От 3 до 40 символов.
- Строчные латинские буквы, цифры и дефисы.
- Начало и конец — буква или цифра.
- Уникальность обеспечивается ограничением БД.
- Системные адреса вроде `admin`, `login`, `register`, `api` недоступны.

Форма предлагает вариант из имени, но тренер может его изменить.

В блоке А адрес можно менять. Сохранение старых ссылок и перенаправления не реализуются, поскольку публичная запись ещё отсутствует.

В панели показывается будущий адрес с пояснением, что клиентская страница появится в следующем блоке. Кнопки, ведущей на несуществующий виджет, нет.

### 4.3. Фото

Поддерживаем JPEG, PNG и WebP, максимум 5 МБ.

Сервер проверяет реальный формат изображения, приводит его к размеру не более 1 024 × 1 024 и удаляет метаданные. SVG не принимаем.

Новое изображение заменяет старое только после успешного сохранения. Неудачная загрузка сохраняет прежнее фото.

### 4.4. Часовой пояс

По умолчанию — `Europe/Moscow`, с возможностью выбора другого значения.

Недельный график хранится как локальное время тренера. Технические даты создания и изменения — UTC.

При смене часового пояса интервалы «09:00–18:00» остаются такими же местными интервалами. В блоке А ещё нет бронирований, которые пришлось бы пересчитывать.

## 5. Недельный график

### 5.1. Возможности

Экран содержит семь дней недели, с понедельника по воскресенье.

Для каждого дня тренер может:

- Сделать день рабочим или выходным.
- Добавить несколько интервалов.
- Изменить или удалить интервал.
- Скопировать интервалы на выбранные дни.

Пример:

- Понедельник: 09:00–13:00 и 15:00–20:00.
- Вторник: 10:00–18:00.
- Воскресенье: выходной.

Обед — промежуток между рабочими интервалами, отдельная сущность не нужна.

### 5.2. Проверки

- Начало раньше окончания.
- Интервалы не пересекаются.
- Соседние интервалы без перерыва объединяются.
- Максимум восемь интервалов в день.
- Время задаётся с точностью до минуты.
- Интервалы через полночь не поддерживаются.
- `24:00` допустимо только как окончание дня.

День без интервалов считается выходным.

При сохранении проверяется весь недельный график. Если есть ошибка, прежний график остаётся целиком: частичное сохранение недопустимо.

Изначально все дни — выходные. Не создаём предположительно свободное время без решения тренера.

### 5.3. Ограничения блока

Не реализуем исключения на конкретную дату, отпуск, праздники, календарь записей и генерацию слотов.

Если длительность услуги не помещается ни в один рабочий интервал с учётом буферов, показываем предупреждение. Это не запрещает сохранить услугу или график.

## 6. Каталог услуг

### 6.1. Поля услуги

| Поле | Требование |
|---|---|
| Название | Обязательно, до 100 символов |
| Описание | Необязательно, до 2 000 символов |
| Тип | Персональная или сплит |
| Формат | Очно или онлайн |
| Длительность | От 15 до 240 минут, шаг 5 минут |
| Цена | От 0 до 1 000 000 ₽, точность до копейки |
| Максимум участников | Персональная — 1; сплит — 2 |
| Место проведения | Необязательно; для очных услуг |
| Активность | Включена или отключена |

«Онлайн» является форматом, а не отдельным типом. Поэтому доступны персональное онлайн-занятие и онлайн-сплит.

Групповые занятия более чем на двух участников в эту версию не входят.

Цена означает **цену за одного участника**. Оплата и списание денег здесь не реализуются.

Деньги хранятся целым числом копеек, без вычислений через дробные числа.

### 6.2. Операции

Тренер может:

- Просмотреть список своих услуг.
- Создать услугу.
- Редактировать её.
- Включить или отключить.

Новая услуга по умолчанию: персональная, очная, 60 минут, один участник. Цену тренер вводит самостоятельно.

Физическое удаление через интерфейс не предоставляем. Отключение позволит в дальнейшем сохранить ссылки из истории тренировок.

Названия услуг могут повторяться.

### 6.3. Отображение

В списке видны название, тип, формат, длительность, цена, вместимость и статус.

Для пустого каталога показывается действие «Добавить первую услугу».

Отключённые услуги остаются доступными тренеру для редактирования, но в будущем не участвуют в самозаписи.

## 7. Буферы и правила записи

Настройки общие для всех услуг тренера.

| Настройка | Значение по умолчанию | Допустимый диапазон |
|---|---:|---:|
| Буфер до занятия | 0 минут | 0–120 минут |
| Буфер после занятия | 10 минут | 0–120 минут |
| Минимальное время до начала | 120 минут | 0–10 080 минут |
| Горизонт записи | 30 дней | 1–90 дней |
| Шаг начала занятий | 15 минут | 5, 10, 15, 20, 30 или 60 минут |
| Срок самостоятельной отмены | 12 часов | 0–168 часов |
| Срок самостоятельного переноса | 12 часов | 0–168 часов |

На экране минуты и часы отображаются в понятном пользователю виде. В хранилище временные ограничения сохраняются в минутах.

Правила трактуются следующим образом:

- Буфер занимает время тренера, но не увеличивает длительность услуги для клиента.
- Услуга и оба буфера должны помещаться внутри рабочего интервала.
- Два соседних занятия должны удовлетворять обоим ограничениям буфера; требуемая пауза равна большему из буфера после первого и буфера до второго.
- Ровно на границе установленного срока запись, отмена или перенос разрешены.
- Горизонт считается по местным календарным датам тренера.
- Шаг начала задаёт сетку времени от местной полуночи.

Блок А сохраняет эти параметры и проверяет их согласованность. Например, минимальное время до занятия не должно делать весь горизонт записи недоступным.

Штрафы, списание занятий и возвраты не настраиваются.

## 8. Экраны и пользовательский путь

### 8.1. Экраны авторизации

Регистрация, вход, подтверждение email, запрос восстановления, установка пароля и завершение регистрации через Telegram.

### 8.2. Навигация панели

- Обзор.
- Профиль.
- Недельный график.
- Услуги.
- Правила записи.
- Настройки доступа.

Обзор показывает состояние подготовки пространства и ссылки на незавершённые шаги.

Статус **«Базовая настройка завершена»** появляется, когда заполнены имя, `slug` и часовой пояс, есть хотя бы один рабочий интервал и одна активная услуга.

Фото, описание, телефон и адрес не блокируют завершение.

Этот статус не означает публикацию клиентской страницы.

### 8.3. Поведение интерфейса

- Язык — русский.
- Светлая тема.
- Основной акцент — зелёный; единые компоненты форм и кнопок.
- Поддержка экранов от 360 px без горизонтальной прокрутки.
- Подписи полей, управление клавиатурой и видимый фокус.
- Ошибки рядом с полями.
- Уведомление об успешном сохранении.
- Защита от повторного нажатия во время запроса.
- Предупреждение при уходе с несохранённой формы.
- Данные после сохранения и обновления страницы совпадают.

Автосохранение не используем: у каждого раздела явная кнопка «Сохранить».

## 9. Данные, интерфейсы и события

### 9.1. Основные сущности

| Сущность | Назначение |
|---|---|
| Пользователь | Email, пароль при наличии, подтверждение email |
| Telegram identity | Проверенный идентификатор Telegram, связь с пользователем |
| Рабочее пространство | Владелец, профиль, часовой пояс, `slug`, фото |
| Рабочий интервал | Пространство, день недели, начало и окончание |
| Услуга | Пространство, тип, формат, длительность, цена, вместимость, активность |
| Правила записи | Буферы и временные ограничения пространства |

Единственность пространства владельца, `slug` и Telegram identity обеспечивается ограничениями БД.

График и услуги принадлежат пространству. Клиент браузера не определяет владельца через переданный `workspace_id`: сервер получает его из текущего пользователя.

Начальное состояние пространства: пустой график, пустой каталог, правила по умолчанию.

### 9.2. Веб-интерфейсы

Закрытые разделы размещаются под `/app`.

Основные операции:

- Просмотр и обновление профиля.
- Чтение и полная замена недельного графика.
- Просмотр, создание и обновление услуги.
- Изменение активности услуги.
- Чтение и обновление правил.
- Управление способом входа.

Используем серверные маршруты Laravel и Inertia. Отдельный публичный REST API и токены API в блоке А не создаём.

### 9.3. Доменные события

После успешного сохранения публикуются внутренние события:

- `WorkspaceCreated`.
- `TrainerProfileUpdated`.
- `WeeklyScheduleUpdated`.
- `BookingRulesUpdated`.
- `ServiceCreated`.
- `ServiceUpdated`.
- `ServiceStatusChanged`.

Событие содержит идентификатор события, пространство, объект и время возникновения. Секреты и лишние персональные данные в него не включаются.

События отправляются после фиксации транзакции. Обработчики с внешними действиями ставятся в очередь.

Здесь это механизм событий Laravel. Гарантированную доставку событий между отдельными микросервисами пока не обещаем и отдельный распределённый протокол не строим.

## 10. Надёжность и эксплуатация

### 10.1. Изоляция

Тренер не может читать или изменять чужие профиль, график, правила, услуги или фото, включая запросы с вручную подменёнными идентификаторами.

Проверки выполняются на сервере, а не только скрытием кнопок.

### 10.2. Очереди и письма

Настраиваем отсутствующее подключение RabbitMQ и отдельную очередь писем.

Фоновые задачи используют ограниченное число повторов с увеличением паузы. Сбой отправки письма не удаляет созданный аккаунт.

Повторная доставка одной задачи не должна создавать аккаунты или повторно менять состояние пространства.

В production нужен SMTP-провайдер. В локальном окружении используем Mailpit для проверки писем без отправки реальным пользователям.

### 10.3. Производительность

Требование менее 200 мс относится к будущему публичному виджету и не проверяется на несуществующем блоке Б.

Для блока А принимаем цель: p95 серверного ответа внутренних страниц и обычных сохранений — до 500 мс при 20 одновременных пользователях в документированном тестовом окружении. Проверка проводится на подготовленной БД и исключает внешнюю Telegram-авторизацию и загрузку фото.

Фактические результаты измерений фиксируются в отчёте.

### 10.4. Конфигурация

В `.env.example` описываем параметры PostgreSQL, Redis, RabbitMQ, SMTP/Mailpit, публичного адреса и Telegram Login.

Секреты остаются в `.env`. Нужны отдельные Telegram Client ID и Client Secret и зарегистрированные разрешённые URL.

Если Telegram не настроен, интерфейс явно сообщает о недоступности способа входа. Поддельную авторизацию для обхода настройки не делаем.

## 11. Последовательность реализации

**Рекомендуемый формат — по частям, но по одному общему ТЗ и одному ExecPlan.** Так каждая часть даёт проверяемый результат, а ошибки авторизации или модели данных обнаруживаются до разработки всех экранов.

Не нужно повторно проектировать весь блок перед каждой частью.

### Часть 1. Основа приложения и модуля

Подключить Vue, TypeScript, Inertia и Fortify. Подготовить общий интерфейс панели, структуру модуля и миграции. Настроить PostgreSQL, Redis, RabbitMQ и локальную почту.

**Результат:** приложение запускается в согласованном окружении, интерфейс собирается, миграции применяются, тестовая задача и письмо проходят через очередь.

### Часть 2. Регистрация и доступ

Реализовать регистрацию, подтверждение email, вход, восстановление пароля, Telegram и управление привязкой.

**Результат:** оба способа входа работают; пользователь без подтверждённого email не получает доступ к панели; новый пользователь получает ровно одно пространство.

### Часть 3. Профиль пространства

Реализовать профиль, фото, `slug`, часовой пояс и настройки доступа, относящиеся к изменению email и пароля.

**Результат:** тренер заполняет профиль, видит сохранённые данные после перезагрузки и не может обращаться к чужому пространству.

### Часть 4. Недельный график и правила

Реализовать редактор недели, несколько интервалов, копирование дней, буферы и правила записи.

**Результат:** пример с двумя интервалами сохраняется; пересечения отклоняются; ошибочный запрос не заменяет рабочий график.

### Часть 5. Каталог услуг и обзор готовности

Реализовать создание, редактирование и отключение услуг. Завершить экран обзора и подсказки по незаполненным разделам.

**Результат:** можно создать персональное занятие и онлайн-сплит; состояние подготовки корректно меняется после настройки графика и каталога.

### Часть 6. Полная проверка и документация

Проверить весь пользовательский путь, безопасность, ошибки интеграций, мобильный интерфейс и производительность. Подготовить инструкцию запуска и демонстрационные данные.

**Результат:** выполнены критерии приёмки; ограничения и внешние настройки задокументированы.

## 12. Проверки и критерии приёмки

### Автоматические проверки

- Регистрация создаёт аккаунт и пространство атомарно.
- Повторный email, `slug` и Telegram identity отклоняются.
- Без подтверждения email панель недоступна.
- Восстановление работает; истёкшая и использованная ссылки отклоняются.
- Поддельный, просроченный и повторно предъявленный Telegram-токен отклоняется.
- Привязка Telegram не объединяет чужие аккаунты.
- Нельзя отключить последний способ входа.
- Чужие сущности недоступны при подмене идентификатора.
- Несколько интервалов сохраняются; пересечения и переход через полночь отклоняются.
- При ошибке график не меняется частично.
- Цена точно сохраняется в копейках.
- Персональная услуга допускает одного участника, сплит — двух.
- Отключение услуги сохраняет её данные.
- Неверные правила отклоняются.
- Доменные события не отправляются при откате транзакции.

Основные проверки БД запускаются на PostgreSQL, включая ограничения уникальности. SQLite не является единственным основанием для приёмки.

### Браузерная проверка

Полный сценарий: регистрация → письмо → подтверждение → профиль → график → правила → услуги → перезагрузка → выход → повторный вход.

Отдельно проверяются Telegram-вход, восстановление, экран шириной 360 px и сообщения об ошибках.

Для Telegram нужны как автоматические проверки с контролируемыми токенами, так и реальная проверка с настроенным ботом. Имитация не заменяет подтверждение интеграции.

### Общая готовность

Блок принят, когда:

- Все перечисленные возможности работают.
- Пройдены связанные тесты, форматирование и сборка.
- Пользовательские данные сохраняются корректно.
- Подтверждена изоляция двух тренеров.
- Письма доставляются через очередь.
- Инструкция позволяет запустить проект на другом компьютере.
- В интерфейсе нет действий, обещающих ещё не реализованную запись.

## 13. Документы и порядок работы

Это ТЗ фиксирует продуктовые требования.

Перед реализацией на его основе составляется ExecPlan по корневому `PLANS.md`: конкретные изменения, команды, этапы, проверки и способы восстановления после ошибок.

ExecPlan ведётся в течение всей разработки: обновляются прогресс, решения, обнаруженные особенности и результаты.

Рекомендуемые документы:

- `docs/specs/module-1-block-a.md` — это ТЗ.
